Why the caller remains expensive

The probe keeps twelve integers live across leaf(x) = x + 1. Both default allocators exclude the entire caller-saved bank across every call. They therefore use x19–x28 and two spill homes.

Actual private leaf:
    add x0, x0, #1
    ret

Caller still saves/restores ten GPRs,
stores/reloads two spilled values,
and moves arguments/results through x0.

The leaf leaves x9–x15 untouched. The caller cannot exploit that fact yet. Its register budget therefore stays constrained despite the cheaper leaf.

What could produce larger gains

PriorityWorkExpected mechanism
1Proven leaf clobber summariesKeep caller values in registers that a known callee leaves untouched; reduce spills and save/restore pressure.
2Call-aware operand allocationExpose fixed argument/result registers and internal scratch constraints; reduce moves in non-leaf callers.
3Private aggregate scalarizationReplace proven by-value/result homes with scalar lanes across closed call edges; target QuickJS’s currently excluded value helpers.

Start with private leaf clobber summaries. Keep external/indirect calls conservative, account for hidden TLS/runtime calls and scratch registers, then validate both caller and callee together. Generalizing to non-leaves requires call-graph propagation and recursion handling.

These mechanisms can also benefit known direct C calls. Fast provides freedom to choose a private contract; it still needs allocation and lowering machinery to turn that freedom into speed. ARM’s existing C planner already passes ordinary scalar arguments in x0–x7.

LLVM’s meaning of fastcc

LLVM permits target-specific ABI choices and describes fastcc as an attempt to minimize call cost. It does not specify a universal speedup or one mandatory register assignment. LLVM Language Reference

Ranked engineering priorities

Ranking combines code evidence and workload relevance; it is not a predicted speedup breakdown. Expand/collapse each item.

1Scalar replacement across calls and large CFGsLimited

Stack promotion rejects >256 blocks or >8192 instructions. Exact Full VM event: 956 blocks, 9159 instructions, unchanged. Escaping slot addresses remain conservative; aggregate-return only proves a narrow leaf-constructor pattern.

Next: Bounded per-slot or region-based promotion, then direct aggregate-result field forwarding; preserve capture, initialization, alignment, debug, exception and frame-observer proofs. Merely raising the function cap does not prove accesses promotable.

2Call memory/capture summaries and global memory optimizationMissing general infrastructure

All Call/CallIndirect/Invoke instructions are memory barriers in InstData::memory_effects. FunctionAttrs lacks readonly/readnone or capture summaries. load-reuse is bounded to unique-predecessor chains, 8 edges and 128 facts; no join/loop fixed point. Alias facts recognize constant ptradd paths and restricted roots.

Next: Infer conservative summaries only for legally bound direct callees. Add join-aware memory availability and precise invalidation. Build a MemorySSA-like layer if multiple consumers justify it; MemorySSA alone is not an optimization or a source of alias proofs.

3Inlining profitability and specializationPresent; budget policy gap

QuickJS sorting regression traced to the shared module budget rejecting cheap helpers in all three rounds. Constructor priority also provides real benefits. No general function-specialization framework found in the audited optimizer.

Next: Retain tiny constructor priority; reserve bounded capacity for profitable cheap call sites. Longer term specialize small wrappers for constant arguments, with binding and code-growth limits.

4General loop optimization and SLP vectorizationPattern-based coverage

GCM hoists pure computations. loop-memory recognizes small unrotated two-block loops; Full does not schedule it. Loop vectorizer supports bounded shapes plus specialized reductions; no SLP vectorizer found.

Next: Broader loop facts, guarded invariant memory motion, then SLP packing of adjacent scalar work. Important across general programs; not yet demonstrated to dominate these interpreter workloads.

5Machine scheduling, hot-path layout and allocationBackend maturity gap

Default Fast/Full have one location per SSA value and no interval splitting. Layout follows allocation order. Dedicated target-latency machine scheduling is not present in the audited codegen path. Bounded dispatch-tail replication exists as an explicit experiment.

Next: Use exact hot-path evidence to prioritize layout and dependency scheduling. Existing experimental allocator directions stay parked; this audit does not justify changing the default allocator.

What I would tackle next

1. Fix inlining budget distribution. It has a measured regression and a bounded remedy.

2. Prove more aggregate temporaries private, then promote them efficiently in large functions. Start with one hot VM handler and preserve exact memory/exception behavior.

3. Add reusable call-effect and memory-flow analysis. Let several optimizations consume the same proofs rather than extending isolated patterns indefinitely.

General loop/SLP work and backend scheduling remain valuable, but are weaker first bets for the current interpreter-heavy suite. Missing PGO/LTO is not an explanation for this comparison: the Clang baseline uses neither.

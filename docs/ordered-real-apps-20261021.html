Each pass separately and together: identical IR to cleanup alone on every input. Combined candidate: identical full objects and linked executables, not merely similar instruction counts.

What the controls establish

Default Full → scalar cleanup → reference
Default Full → wide SIMD + state predication → same cleanup → identical application executable

The kernel control activates once for wide SIMD and once for predication, confirming that the candidate passes actually run. Application checks include configured Lua/QuickJS tests and SQLite queries, with benchmark outputs checked against Clang O2.

No promotion into Full. There is no incremental application code change to benchmark. Both passes remain available for their supported loop workloads; this result does not remove production SIMD instruction selection.

Why applicability is narrow

  • Wide adjacent SIMD requires an entire small function containing the exact adjacent-difference loop. It cannot currently match the loop inside a large interpreter function.
  • Running-state predication requires a specific credit/debit recurrence, including debit by 17. It is a loop idiom recognizer, not general branch elimination.

Where to put the next optimization effort

Return to the hottest Lua/QuickJS functions and their actual memory traffic, aggregate lowering and branch sequences. Require a transformation hit in measured application code before extending another benchmark-specific recognizer.

Scope, evidence and reproduction

Fresh compiler built from current source, then frozen by SHA-256. Actual default Full schedule discovered from its optimization report: 62 passes. Compared default, cleanup-only, wide, state, and both on 44 prepared application inputs plus one kernel control.

Cleanup alone changes IR in 11 application inputs. Those changes are separate from the two nonmatching loop passes. No timing claim is made for cleanup.

All application builds used a common Clang link step and unchanged inputs; comparison checks complete object bytes and executable hashes. No runtime timing campaign was needed for byte-identical candidate executables. No new x86 execution or default change.
